# 测试类型设计方法与覆盖要点
# Test Type Design Methods & Coverage Guide
# 版本: v1.0
# 作用: 每种测试类型的完整方法论、设计模板、覆盖清单、输出焦点
# 加载策略: 用例生成阶段4和报告生成步骤3/4按需引用

---

## 一、类型全景

| 标识 | 类型 | 核心目标 | 主要方法 | 典型产出密度 |
|------|------|---------|---------|-------------|
| F | 功能测试 | 验证功能正确性 | 等价类/边界值/场景法/判定表 | 高（占总量 40-50%） |
| I | 接口测试 | 验证 API 契约、数据交换 | 参数组合/状态码覆盖/契约校验 | 中（占总量 15-20%） |
| P | 性能测试 | 验证系统性能指标 | 负载/压力/稳定性/基准测试 | 低（占总量 5-10%） |
| S | 安全测试 | 验证安全防护能力 | 渗透测试/权限矩阵/注入测试 | 低（占总量 5-10%） |
| C | 兼容性测试 | 验证多环境一致性 | 矩阵覆盖/等价设备/分辨率遍历 | 低（占总量 5-8%） |
| U | 用户体验测试 | 验证交互与可用性 | 启发式评估/认知走查/A/B对比 | 低（占总量 5-8%） |
| E | 异常边界测试 | 验证系统容错能力 | 边界值/错误推测/故障注入 | 中（占总量 10-15%） |
| N | 用户视角测试 | 以真实用户思维发现盲区 | 新手探索/非预期路径/直觉偏差 | 低（占总量 5-8%） |
| R | 回归测试 | 验证已有功能不受变更影响 | 相近度分层/用例复用/门禁冒烟 | 按变更规模浮动 |

## 二、各类型详细方法论

---

### F — 功能测试 (Functional)

**目标**: 验证功能逻辑的正确性，确保系统按需求定义执行

**设计方法**:

| 方法 | 适用场景 | 用例生成规则 |
|------|---------|------------|
| **等价类划分** | 输入数据有范围/类型/格式约束 | 有效等价类：各取1代表值；无效等价类：各取1代表值 |
| **边界值分析** | 输入/输出有明确数值边界 | 边界值、边界值±1、边界值两端极值 |
| **场景法** | 有明确用户操作流程 | 基本流（Happy Path）+ 备选流（分支）+ 异常流 |
| **判定表/因果图** | 多条件组合产生不同结果 | 条件穷举 → 简化 → 每行1条用例 |
| **状态迁移** | 功能涉及状态变化 | 状态节点覆盖 + 迁移路径覆盖 + 无效迁移 |
| **正交实验** | 多参数组合，无法全组合 | 选正交表 Ln(m^k)，减少用例但保持覆盖 |

**覆盖要点**:
- [ ] 正向流程：每个 Happy Path 至少 1 条
- [ ] 逆向流程：操作取消/返回/退出
- [ ] 分支逻辑：if-else / switch-case 每个分支
- [ ] 默认值：字段默认值、页面初始状态
- [ ] 数据精度：金额小数位、百分比舍入
- [ ] 幂等性：同一操作重复执行结果一致
- [ ] 数据持久化：操作后数据库/缓存正确更新
- [ ] 搜索/筛选：单条件、组合条件、模糊搜索、精确匹配
- [ ] 分页/排序：首页/末页/翻页/自定义排序

**用例示例模板**:
```
【正向流程】TC-{MODULE}-{FUNC}-NNN-F
  名称: {动词} + {对象} + {场景} + {期望结果}
  步骤:
    1. {前置操作}
    2. {输入有效值}
    3. {触发核心操作}
    4. {验证结果}
  预期: {明确的成功状态 + 数据变化}
```

### I — 接口测试 (Interface/API)

**目标**: 验证 API 接口的契约符合性、数据交换正确性、异常容错性

**设计方法**:

| 方法 | 适用场景 | 用例生成规则 |
|------|---------|------------|
| **参数组合** | 接口有多种参数 | 必填缺失、类型错误、超长截断、特殊字符 |
| **状态码覆盖** | HTTP/gRPC 接口 | 200/201/204/400/401/403/404/409/422/500 |
| **契约校验** | 有 OpenAPI/Proto 定义 | 逐字段比对 response schema，检查类型/必填/格式 |
| **鉴权覆盖** | 需要认证的接口 | 无Token、过期Token、伪造Token、跨用户Token |
| **幂等性验证** | 写操作接口 | 同一请求发送2次，结果一致，无副作用 |
| **超时/重试** | 有网络交互 | 超时后的处理、重试机制、幂等保障 |

**覆盖要点**:
- [ ] 请求参数校验：数据类型/长度/格式/枚举值/必填/默认值
- [ ] 返回值校验：HTTP状态码、response body结构、字段类型、错误码
- [ ] Header 校验：Content-Type、Authorization、自定义Header
- [ ] 异常状态码：400(Bad Request)、401/403(鉴权)、404、409(冲突)、422、429(限流)、500
- [ ] 幂等性：POST/PUT 重复请求数据一致
- [ ] 并发：同一接口并发请求，数据一致、无死锁
- [ ] 鉴权：无Token、过期、跨租户、越权
- [ ] 限流：触发限流后的返回码和提示
- [ ] 分页：page=0、page=-1、超大page、pageSize=0、pageSize>上限
- [ ] 排序：非法字段、SQL注入字段

**用例示例模板**:
```
【接口参数校验】TC-{MODULE}-{FUNC}-NNN-I
  名称: {接口名} + {参数} + {异常值} + 返回{状态码}
  步骤:
    1. 构造请求，{参数}={异常值}
    2. 发送 {METHOD} 请求到 {endpoint}
    3. 检查 HTTP 状态码
    4. 检查 response body 中的错误码和提示
  预期:
    - HTTP 状态码: {预期状态码}
    - 错误码: {预期错误码}
    - 提示信息: {明确的错误文案，非英文技术异常}
```

### P — 性能测试 (Performance)

**目标**: 验证系统在预期负载下的性能指标是否符合SLA

**设计方法**:

| 方法 | 目标 | 执行方式 | 关键指标 |
|------|------|---------|---------|
| **基准测试** | 建立单用户性能基线 | 单用户执行核心接口，取P50/P95/P99 | 响应时间(ms) |
| **负载测试** | 预期并发下的表现 | 逐步加并发至目标值，持续5-15分钟 | TPS、响应时间、错误率 |
| **压力测试** | 找到系统极限 | 持续加并发直到系统崩溃或响应超时 | 极限TPS、崩溃点 |
| **稳定性测试** | 长时间运行的表现 | 目标并发运行 1-8 小时 | 内存泄漏、GC频率、错误率 |
| **峰值测试** | 瞬间流量冲击 | 短时间(1-5s)内突发高并发 | 峰值TPS、恢复时间 |

**关键指标定义**:

| 指标 | 优秀 | 良好 | 需优化 | 不达标 |
|------|------|------|--------|--------|
| 平均响应时间 | < 100ms | < 300ms | < 1000ms | ≥ 1000ms |
| P95 响应时间 | < 200ms | < 500ms | < 2000ms | ≥ 2000ms |
| P99 响应时间 | < 500ms | < 1000ms | < 5000ms | ≥ 5000ms |
| TPS（单接口） | > 1000 | > 500 | > 100 | < 100 |
| 错误率 | < 0.01% | < 0.1% | < 1% | ≥ 1% |
| CPU 使用率 | < 50% | < 70% | < 90% | ≥ 90% |
| 内存使用率 | < 60% | < 80% | < 95% | ≥ 95% |

**覆盖要点**:
- [ ] 核心交易接口（下单/支付/查询）
- [ ] 高频查询接口（列表/搜索/详情）
- [ ] 涉及数据库写操作的接口（关注锁竞争）
- [ ] 涉及缓存读写的接口（关注穿透/击穿）
- [ ] 涉及外部调用的接口（关注超时积压）
- [ ] 涉及大文件传输的接口（上传/下载/导出）
- [ ] 登录/认证接口（高频 + 校验逻辑）
- [ ] 消息队列消费能力（如有）

**用例示例模板**:
```
【负载测试】TC-{MODULE}-{FUNC}-NNN-P
  名称: {接口名}在{N}并发下的负载测试
  前置条件:
    - 测试数据量: {N}条
    - 并发线程数: {threads}
    - 持续时间: {duration}
    - 预热时间: {warmup}s
  预期:
    - 平均响应时间 ≤ {target}ms
    - P95 ≤ {target}p95ms
    - P99 ≤ {target}p99ms
    - 错误率 ≤ {target}error%
    - TPS ≥ {target}tps
```

### S — 安全测试 (Security)

**目标**: 验证系统的安全防护能力，识别漏洞和风险

**设计方法**:

| 方法 | 目标 | 检查范围 |
|------|------|---------|
| **权限矩阵验证** | 确保权限控制正确 | 每个角色 × 每个操作的允许/禁止矩阵 |
| **注入测试** | 防护 SQL/XSS/命令注入 | 所有用户输入点 |
| **越权测试** | 防护水平/垂直越权 | ID枚举、Token替换 |
| **敏感数据保护** | 数据加密/脱敏/掩码 | 传输层、存储层、展示层 |
| **认证安全** | 认证机制的健壮性 | 暴力破解、Session固定、Token安全 |
| **CSRF/XSS** | Web 攻击向量 | 表单提交、URL参数、富文本 |

**覆盖要点**:
- [ ] **认证**: 弱密码拦截、验证码机制、Token过期、多端登录互踢、Session超时
- [ ] **授权**: 水平越权(改ID访问他人数据)、垂直越权(低权限访问高权限接口)
- [ ] **注入**: SQL注入(`' OR '1'='1`)、XSS(`<script>alert(1)</script>`)、命令注入、XXE
- [ ] **数据保护**: HTTPS强制、敏感字段加密存储、日志脱敏、响应掩码
- [ ] **传输安全**: 证书有效性、TLS版本、明文传输检测
- [ ] **CSRF**: 关键操作是否有Token校验
- [ ] **文件上传**: 文件类型校验(不依赖扩展名)、大小限制、恶意文件检测
- [ ] **API 安全**: 频率限制、签名校验、重放攻击
- [ ] **信息泄露**: 错误页面不暴露堆栈、响应头不泄露服务器信息

**用例示例模板**:
```
【越权测试】TC-{MODULE}-{FUNC}-NNN-S
  名称: 用户A尝试访问用户B的{资源类型}应被拒绝
  步骤:
    1. 以用户A身份登录，获取 Token_A
    2. 以用户B身份登录，获取 B 的{资源ID}
    3. 使用 Token_A 请求 /api/{resource}/{B的ID}
    4. 观察响应
  预期:
    - HTTP 状态码: 403 Forbidden 或 404(不暴露资源存在性)
    - 不应返回用户B的数据
```

### C — 兼容性测试 (Compatibility)

**目标**: 验证系统在不同运行环境下的表现一致性

**设计方法**:

| 维度 | 如何选择组合 | 缩减策略 |
|------|------------|---------|
| **浏览器** | Chrome/Firefox/Safari/Edge 最新版 + 次新版 | 选 Top2 + 用户主力浏览器 |
| **操作系统** | Windows/macOS/Linux/iOS/Android | 选 Top2 桌面 + Top2 移动 |
| **设备** | 不同分辨率/屏幕尺寸/设备型号 | 等价分辨率：小(320)/中(375)/大(414/1920) |
| **网络** | WiFi/4G/5G/弱网(3G/2G) | 至少覆盖 WiFi + 弱网 |

**覆盖要点**:
- [ ] 页面布局: 分辨率变化时无错位/重叠/溢出
- [ ] 字体渲染: 不同OS下字体大小一致
- [ ] 表单交互: 日期选择器/下拉框在各浏览器可用
- [ ] Cookie/Storage: 各浏览器存储行为一致
- [ ] CORS: 跨域请求在各浏览器正常
- [ ] 触屏 vs 鼠标: 移动端触控热区足够大（≥ 44pt）
- [ ] 弱网: 加载中状态、超时提示、断网恢复
- [ ] 系统版本: iOS/Android 主流版本（当前+回溯2代）

### U — 用户体验测试 (User Experience)

**目标**: 验证交互流畅度、视觉一致性、操作便捷性

**覆盖要点**:
- [ ] 视觉层次: 信息按重要性分层，核心操作突出
- [ ] 操作反馈: 点击有状态变化、加载有进度、成功/失败有提示
- [ ] 文案质量: 无错别字、无技术术语、提示信息有建设性
- [ ] 页面加载: 首屏 < 2s、骨架屏/loading 有反馈
- [ ] 可访问性: 键盘导航、对比度、标签语义
- [ ] 错误恢复: 操作失败后有明确的重试路径
- [ ] 表单体验: 必填标识、实时校验、错误定位

---

### E — 异常/边界测试 (Exception/Edge)

**目标**: 验证系统在异常条件和极限输入下的容错能力

**覆盖要点**:
- [ ] 数值边界: 最小值-1、最大值+1、0、负数、浮点精度
- [ ] 字符串边界: 空字符串、单字符、最大长度、超长截断
- [ ] 集合边界: 空列表、单元素、最大条数、超限
- [ ] 时间边界: 过去时间、未来时间、跨天/跨月/跨年
- [ ] 网络异常: 超时、断网、DNS失败
- [ ] 服务异常: 下游返回500、超时、返回格式异常
- [ ] 数据异常: NULL字段、脏数据、编码错误
- [ ] 并发冲突: 乐观锁冲突、库存扣减竞争
- [ ] 磁盘/内存异常: 磁盘满、内存溢出

**用例示例模板**:
```
【边界值】TC-{MODULE}-{FUNC}-NNN-E
  名称: {输入字段}输入{边界值}的处理
  步骤:
    1. {前置条件}
    2. 在{字段}输入{边界值}
    3. 提交操作
  预期:
    - {具体的系统行为}（拒绝并提示/接受并截断/接受并存储）
```

### N — 用户视角测试 (User Perspective)

> 详细方法参见 `frameworks/user-perspective-checklist.md`

**三类用例**:
1. **新手探索式**: 无培训、凭直觉上手 → 3秒认知、首要操作识别、空状态引导
2. **非预期路径**: 不走常规流程 → 快速连击、浏览器后退、多Tab、断网恢复
3. **直觉偏差**: 用户主观理解与系统行为不一致 → 提交≠成功、删除≠彻底删除、退出≠切换账号

---

### R — 回归测试 (Regression)

> 详细方法参见 `frameworks/proximity-model.md`

**分层策略**:
| 相近度 | 等级 | 原有用例复用 | 新增补充用例 |
|--------|------|------------|------------|
| ≥ 4.0 | 高 | 100% 全量 | 接口兼容性 + 数据一致性 + 端到端串联 |
| 2.0-3.9 | 中 | P0/P1 用例 | 核心流程端到端 + 关键接口验证 |
| 1.0-1.9 | 低 | P0 冒烟用例 | 核心流程冒烟 |
| 0.1-0.9 | 微 | 核心冒烟 | 无 |
| 0.0 | 无关 | 无 | 仅全系统核心链路冒烟 |

## 三、用户指定类型时的自适应策略

### 3.1 识别用户意图

当用户表述中包含以下关键词时，自动将测试重心倾向对应类型：

| 用户表述 | 识别为 | 策略调整 |
|---------|--------|---------|
| "功能测试"/"测功能"/"验证功能"/"业务逻辑" | F-功能测试为主 | 功能用例占比提升至 60-70%，侧重等价类+场景法+判定表 |
| "接口测试"/"API测试"/"测接口"/"接口文档" | I-接口测试为主 | 接口用例占比提升至 40-50%，侧重参数组合+状态码+契约校验 |
| "性能测试"/"压测"/"并发"/"响应时间"/"TPS" | P-性能测试为主 | 性能用例占比提升至 20-30%，含基准/负载/压力/稳定性 |
| "安全测试"/"渗透"/"漏洞"/"越权"/"SQL注入" | S-安全测试为主 | 安全用例占比提升至 20-30%，侧重权限矩阵+注入+越权 |
| "兼容性"/"多浏览器"/"多端"/"适配" | C-兼容性测试为主 | 兼容性用例占比提升至 15-20%，侧重浏览器矩阵+分辨率 |
| "体验"/"交互"/"UI"/"可用性" | U-UX测试为主 | UX用例占比提升至 10-15% |
| "异常"/"边界"/"容错"/"极限" | E-异常边界为主 | 异常用例占比提升至 25-35% |
| "用户视角"/"新手"/"小白" | N-用户视角为主 | 用户视角用例提升至 15-20% |
| "回归测试"/"全量"/"全面" | 全类型均衡 | 每种类型按默认比例 |

### 3.2 多类型组合

如果用户说 **"功能+接口测试"** 或 **"功能和性能测试"**，则：
- 主类型的用例占比提升（不低于 60%），覆盖深度加满
- 辅类型的用例覆盖基础场景（不低于 10%）
- 其他类型保持最低覆盖（每模块至少 1-2 条冒烟）

### 3.3 反问确认

当识别到用户指定了测试类型，在阶段3追加以下反问：

```markdown
📌 检测到您侧重 {检测到的类型} 测试，已自动调整用例分布：

| 测试类型 | 默认占比 | 本次占比 |
|---------|---------|---------|
| {检测到的主类型} | {默认%} | {调整后%} ↑ |
| 其他 | ... | ... |

确认以下问题：
1. {主类型}的测试深度：基础覆盖 / 中等覆盖 / 深度覆盖（含极端场景）？
2. 是否还需要额外补充其他类型的测试？如有，补充哪些？
3. 测试执行周期是否允许全量执行？还是需要精选核心用例优先？
```

## 四、按类型生成报告的统计口径

在测试报告生成的步骤3中，按类型增加以下统计维度：

### 各类型通过率对比

|---------|--------|--------|------|------|------|--------|---------|
| 功能测试 | | | | | | | |
| 接口测试 | | | | | | | |
| 性能测试 | | | | | | | |
| 安全测试 | | | | | | | |
| 兼容性测试 | | | | | | | |
| 用户体验测试 | | | | | | | |
