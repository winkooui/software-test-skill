# 需求可测试性分析检查清单
# Testability Analysis Checklist
# 版本: v1.0
# 作用: 测试左移阶段使用，评估需求的可测试性，提前识别风险和模糊点

---

## 一、评估维度总览

| 维度 | 权重 | 目标 |
|------|------|------|
| 需求清晰度 | 25% | 需求表述无歧义，各方理解一致 |
| 可验证性 | 25% | 存在明确的客观手段验证需求是否满足 |
| 完整性 | 20% | 需求覆盖了正常、异常、边界场景 |
| 数据可获取性 | 15% | 测试所需数据可以准备或模拟 |
| 依赖清晰度 | 15% | 外部依赖和接口契约明确 |

---

## 二、逐项检查清单

### 2.1 需求清晰度（25%）

| # | 检查项 | 通过标准 | 不通过示例 |
|----|--------|---------|-----------|
| 1 | 功能描述无模糊词 | 无"快速""尽量""较好""合理"等无法量化的词 | ❌ "页面响应要快" |
| 2 | 输入输出有明确定义 | 每个输入的数据类型、范围、必填性已定义 | ❌ "支持多种支付方式"（未列出具体方式） |
| 3 | 业务规则可执行 | 条件分支逻辑完整，无"视情况而定" | ❌ "根据用户等级决定"（未说明各等级的规则） |
| 4 | 术语一致 | 同一概念在整个文档中名称统一 | ❌ 文档中"订单"有时叫"交易单" |
| 5 | UI 有原型或明确描述 | 页面布局、交互行为有参考 | ❌ "一个好看的登录页" |

### 2.2 可验证性（25%）

| # | 检查项 | 通过标准 | 评估方法 |
|----|--------|---------|---------|
| 1 | 功能性需求可测试 | 可以通过操作 + 观察来验证 | 有没有对应的"预期结果"？ |
| 2 | 非功能性需求可度量 | 性能、安全等要求有具体指标 | "响应时间 < 200ms" ✅ 非"响应要快" ❌ |
| 3 | 验收标准明确 | 定义了 Done 的条件 | "P0 用例 100% 通过，整体通过率 ≥ 95%" |
| 4 | 有回滚标准 | 定义了失败的底线 | "如果支付成功率 < 99%，即回滚" |

### 2.3 完整性（20%）

| # | 检查项 | 通过标准 |
|----|--------|---------|
| 1 | 正常流程完整 | 从起点到终点的 Happy Path 描述完整 |
| 2 | 异常场景覆盖 | 至少覆盖：网络异常、超时、数据异常、并发冲突 |
| 3 | 边界条件明确 | 输入范围的最大值/最小值、空值、超长值有定义 |
| 4 | 权限模型说明 | 不同角色的操作权限有定义 |
| 5 | 状态机清晰 | 如有状态流转，各状态及其转换条件已定义 |

### 2.4 数据可获取性（15%）

| # | 检查项 | 通过标准 |
|----|--------|---------|
| 1 | 测试数据来源明确 | 测试数据可以从哪里获取（生成/脱敏/Mock） |
| 2 | 敏感数据有替代方案 | 涉及身份证、银行卡等时有测试专用值 |
| 3 | 第三方数据有 Mock 方案 | 外部依赖有可用的 Mock 服务或沙箱 |
| 4 | 数据量大时可行 | 如果需要百万级数据，有批量生成方案 |

### 2.5 依赖清晰度（15%）

| # | 检查项 | 通过标准 |
|----|--------|---------|
| 1 | 外部接口契约明确 | 调用第三方的 API 文档/协议已提供 |
| 2 | 超时和降级策略 | 外部依赖不可用时的处理逻辑已定义 |
| 3 | 版本兼容性说明 | 如果有版本升级，兼容性方案已说明 |
| 4 | 环境依赖清单 | 测试需要哪些环境组件（数据库版本、中间件等）已列出 |

---

## 三、评分规则

### 每项评分
- 2 分：完全满足，无问题
- 1 分：部分满足，存在轻微模糊
- 0 分：不满足，存在明显缺陷

### 总体评分
```
可测试性评分 = (所有子项得分之和 / (总项数 × 2)) × 10
结果范围：0 ~ 10
```

### 风险判定
| 评分 | 风险等级 | 处理建议 |
|------|---------|---------|
| ≥ 8 | 🟢 低 | 可正常进入测试设计 |
| 6 - 7.9 | 🟡 中 | 建议补充模糊项后再设计测试用例 |
| 4 - 5.9 | 🟠 高 | 建议退回需求方补充，存在明显测试风险 |
| < 4 | 🔴 严重 | 不可测试，需重新澄清需求 |

## 四、快速自评表

| 核心问题 | 是/否 |
|---------|-------|
| 我能闭着眼睛说出这个功能"成功"长什么样吗？ | |
| 我能明确写出每个输入的有效和无效值吗？ | |
| 我知道当依赖的服务挂了，这个功能应该怎么表现吗？ | |
| 我能在一个隔离的环境（非生产）中完整验证吗？ | |
| 我能确信测试数据和真实数据在结构上一致吗？ | |

> 如果以上有任何一个答案是"否"，请标记为高风险项并反馈给需求方。
