# 相近度计算模型（详细版）
# Proximity Calculation Model
# 版本: v1.0
# 作用: 量化变更对已有功能的影响程度，为回归测试范围提供数据依据

---

## 一、模型概述

### 用途
按一个新增/修改的变更点，对系统中每个已有功能点计算"综合相近度"分数。
分数越高 → 越容易被变更影响 → 回归测试深度越大。

### 计算公式
```
综合相近度 = 代码×0.30 + 数据×0.25 + API×0.20 + 业务×0.15 + UI×0.10
结果范围: 0.0 ~ 5.0
```

### 权重设计原理
| 维度 | 权重 | 理由 |
|------|------|------|
| 代码 | 30% | 代码改动是最直接的变更来源，共用代码变更风险最高 |
| 数据 | 25% | 数据层变更影响面广且隐蔽（SQL、缓存、序列化） |
| API | 20% | 接口变更直接影响调用方和被调用方的兼容性 |
| 业务 | 15% | 业务流程上下游受影响时，端到端体验会断裂 |
| UI | 10% | UI 变更相对独立，通常不引起后端逻辑问题 |

## 二、各维度评分标准

### 2.1 代码相近度（权重 0.30）

| 分数 | 定义 | 判定依据 | 示例 |
|------|------|---------|------|
| 0 | 无关 | 两个功能不在同一代码仓库 | 商品模块 vs 对账模块，代码无交集 |
| 1 | 同仓库 | 在同一 Git 仓库但不同模块 | 同一 monorepo，但属于不同子项目 |
| 2 | 同模块 | 在同一模块目录下 | 都在 order-service 模块 |
| 3 | 同包/同目录 | 在同一 Java Package 或目录 | 都在 com.example.order.service |
| 4 | 同文件 | 修改了同一文件中的代码 | 两个功能都引用了 PaymentUtil.java |
| 5 | 同一函数 | 变更直接修改了某函数/方法的实现 | 修改了 processPayment()，两个功能都调用它 |

### 2.2 数据相近度（权重 0.25）

| 分数 | 定义 | 判定依据 |
|------|------|---------|
| 0 | 无关 | 两个功能不操作同一数据库 |
| 1 | 同库 | 操作同一个数据库实例，但不同 Schema |
| 2 | 同 Schema | 操作同一个 Schema/表空间 |
| 3 | 同表 | 读写同一张数据库表 |
| 4 | 同字段 | 读写表中的同一字段（含新增字段） |
| 5 | 同一行数据 | 操作业务含义上"同一记录"（如同一个订单的同一状态字段） |

### 2.3 API 相近度（权重 0.20）

| 分数 | 定义 | 判定依据 |
|------|------|---------|
| 0 | 无关 | 两个功能不涉及任何 API 调用关系 |
| 1 | 同网关 | 请求经过同一个 API Gateway |
| 2 | 同服务 | 调用同一个微服务（不同端点） |
| 3 | 同 Controller | 调用同一个 Controller（不同方法） |
| 4 | 同接口(不同方法) | 调用同一个 REST 路径，但 HTTP 方法不同 |
| 5 | 同接口 | 调用完全相同的 API 端点 |

### 2.4 业务相近度（权重 0.15）

| 分数 | 定义 | 判定依据 |
|------|------|---------|
| 0 | 无关 | 两个功能在不同的业务领域中 | 
| 1 | 同领域 | 在同一业务上下文中（如同一 Bounded Context） |
| 2 | 上下游(隔 2 步+) | 变更点在业务流程中间，该功能与它隔了 2 个以上环节 |
| 3 | 上下游(隔 1 步) | 该功能是变更点的直接上游或直接下游 |
| 4 | 直接前序/后序 | 数据或状态直接从前一个环节流转到下一个 |
| 5 | 同一子流程 | 两者属于同一子流程的紧密耦合部分 |

### 2.5 UI 相近度（权重 0.10）

| 分数 | 定义 | 判定依据 |
|------|------|---------|
| 0 | 无关 | 两个功能不在同一应用内 |
| 1 | 同应用 | 属于同一个前端应用，但不同菜单 |
| 2 | 同菜单 | 在导航菜单的同一分组下 |
| 3 | 同页面不同区域 | 在同一个页面上，但属于不同区域/组件 |
| 4 | 同区域相邻 | 在同一个功能区域内，组件紧邻 |
| 5 | 同一组件 | 使用完全相同的 UI 组件 |

## 三、分级与回归策略

| 等级 | 分数区间 | 回归深度 | 原有用例复用比例 | 新增回归用例 | 执行环境 |
|------|---------|---------|----------------|-------------|---------|
| 📛 高 | ≥ 4.0 | 深度回归 | 100% 全量用例 | + 接口兼容 + 数据一致性 + 端到端串联 | 沙箱+SIT+UAT+生产 |
| 🟠 中 | 2.0 - 3.9 | 重点回归 | P0/P1 用例 | + 核心流程端到端 + 关键接口验证 | 沙箱+SIT+UAT |
| 🟡 低 | 1.0 - 1.9 | 冒烟回归 | P0 冒烟用例 | + 核心流程冒烟 | 沙箱+SIT |
| 🟢 微 | 0.1 - 0.9 | 极简回归 | 核心冒烟 | 无 | 沙箱 |
| ⚪ 无关 | 0.0 | 不回归 | 无 | 仅全系统核心链路冒烟 | 沙箱+SIT |

## 四、计算示例

### 场景：新增对接 A 方支付接口

| 已有功能 | 代码 | 数据 | API | 业务 | UI | 综合 | 等级 | 回归 |
|---------|------|------|-----|------|-----|------|------|------|
| 订单创建 | 4 (同PaymentUtil) | 5 (同t_order) | 3 (同Controller) | 5 (上游) | 2 (同菜单) | 4.10 | 高 | 深度 |
| 支付回调 | 5 (同Service) | 4 (同t_transaction) | 5 (同端点) | 5 (同流程) | 1 (同应用) | 4.45 | 高 | 深度 |
| 微信支付 | 4 (共用Util) | 2 (同库不同表) | 3 (同网关) | 4 (同流程) | 3 (同页面) | 3.30 | 中 | 重点 |
| 退款申请 | 3 (同包) | 3 (同表) | 3 (同服务) | 4 (下游) | 1 | 2.90 | 中 | 重点 |
| 日对账 | 2 (同模块) | 4 (同字段) | 2 (同服务) | 3 (下游) | 0 | 2.55 | 中 | 重点 |
| 个人中心 | 1 (同仓库) | 2 (同库) | 0 | 1 (同领域) | 2 (同菜单) | 1.20 | 低 | 冒烟 |
| 商品列表 | 0 | 0 | 0 | 0 | 0 | 0.00 | 无关 | 无 |

## 五、校准规则

### 特殊调整规则
1. **历史高频缺陷模块** — 如果某模块在过去 3 个版本内产生过线上缺陷，等级自动提升一级
2. **核心支付/资金模块** — 不论相近度多少，至少按「中相近」处理
3. **共用中间件变更** — 如果变更涉及共用拦截器/过滤器/中间件，所有通过它的接口 API 相近度 +1
4. **数据库迁移** — 如果变更包含 DDL 操作，所有读写该表的功能数据相近度不低于 3
